## 1. 文档用途与状态说明

本文件明确产品目标、版本边界、质量要求和验收条件。具体目录、接口、库选型及构建实现放入后续技术设计。

- **已确认**：用户明确提出的目标和限制。
- **验收提案**：将目标转化为可检查的行为，供后续设计和评审使用。
- **待定**：尚未决定的细节，不作为已经完成或已经承诺的能力。

当前第一版为“架构基础版”。成功标准是基础能力稳定、职责清楚、能够验证后续扩展方式；业务功能数量不是第一版目标。不能以“架构搭好了”代替可运行程序和具体证据。

## 3. 产品目标与第一版目标

### 3.1 长期产品目标

面向星露谷玩家，在统一界面中管理 Mod、配置 SMAPI，并启动游戏。降低手动管理文件和理解安装流程的难度。

### 3.2 第一版目标（已确认方向，以下为验收提案）

交付一个能在约定桌面环境构建和运行的应用基础，至少能够：

1. 打开应用并进入一致的基础界面和设置页面。
2. 使用简体中文、英语、日语，运行时切换并保存选择。
3. 在重启后恢复有效设置，并处理配置缺失、损坏及读写失败。
4. 通过真实的前后端设置读写流程验证模块通信和错误传递。
5. 验证增加语言、增加功能模块及增加平台适配的方式。
6. 通过自动检查和各平台运行验证支撑“稳定、健壮”的结论。

无需已安装星露谷或 SMAPI，也应能运行第一版基础界面与设置。

### 3.3 第一版业务边界

以下业务功能不纳入第一版交付要求：游戏目录自动发现、Mod 扫描和安装、启用停用、依赖检查、SMAPI 安装与更新、游戏启动、在线下载、多套 Mod 方案。

这些是后续产品能力，并非取消需求。第一版可以说明产品用途，但不应提供看似可用、实际只返回假成功的业务按钮。

## 4. 架构质量要求（验收提案）

| 编号 | 要求 | 验收方式 |
| --- | --- | --- |
| ARCH-01 | 展示、业务规则、平台操作的职责清楚 | 页面不直接拼装系统命令或实现安装规则；业务模块不依赖具体 Vue 页面 |
| ARCH-02 | 前后端通信集中管理，输入、结果和错误结构明确 | 设置读写使用真实接口；校验无效输入；前后端数据不一致可被检查发现 |
| ARCH-03 | 功能模块可以独立扩展 | 用可丢弃的示例模块验证接入；接入点和修改位置有文档，不需要重写应用启动流程 |
| ARCH-04 | 系统差异集中在平台适配处 | 路径、进程和系统能力不在页面各处按平台分支；新增平台的适配位置明确 |
| ARCH-05 | 平台能力可以声明支持或不支持 | 不支持的能力返回统一结果；界面能解释原因，不发生崩溃或假成功 |
| ARCH-06 | 初始化与异常恢复行为明确 | 设置加载、语言初始化有确定顺序；失败有可用提示及恢复入口 |
| ARCH-07 | 基础测试不依赖真实游戏安装 | 设置、语言发现、错误转换等基础行为可使用临时目录和受控输入验证 |
| ARCH-08 | 抽象与已知需求对应 | 第一版不预建未使用的插件市场、通用任务框架或复杂继承体系；未来业务的边界可先写设计文档 |

采用何种目录组织、接口定义或类型生成机制，留给技术设计决定。除新增语言外，新增功能或平台可以需要增加适配代码和少量明确的接入配置，不要求所有扩展都实现“零代码”。

## 5. 桌面平台与未来扩展

### 5.1 桌面支持矩阵

| 系统族 | 第一版目标 | 发布前需要确定 |
| --- | --- | --- |
| Windows | 构建并运行架构基础版，验证设置持久化和三种语言 | 最低系统版本、处理器架构、安装包格式、运行依赖 |
| macOS | 构建并运行相同基础能力，保持系统交互合理 | 最低系统版本、Intel / Apple Silicon 范围、包格式及分发方式 |
| Linux | 在明确的发行版环境构建和运行相同基础能力 | 基准发行版及版本、处理器架构、包格式、系统依赖和桌面环境 |

三种系统均为目标，未实测的平台必须标记为“未验证”，不能用单平台编译通过替代跨平台支持。

每个最终选定的“系统 + 版本 + 架构”组合应记录构建结果、启动结果、语言切换和设置读写验证结果。桌面安装包格式、签名和公开分发条件在发布方案中明确。

### 5.2 为其他平台预留的边界

1. 将业务数据和规则与窗口、文件系统、进程启动等能力分开。
2. 通过平台能力判断功能是否可用，避免默认所有平台都可以安装 SMAPI 或访问游戏目录。
3. 对话框、用户数据目录、外部程序启动等系统交互应有明确接入位置。
4. 界面布局使用可调整空间，避免业务流程依赖固定像素窗口尺寸。
5. 后续新增平台仍需相应构建、权限、交互和运行验证；第一版不实现未确定的平台适配。

## 6. 国际化要求

### 6.1 初始语言与覆盖范围（已确认语言，验收提案）

- 简体中文：zh-CN。
- 英语：en。
- 日语：ja。
- 覆盖应用自行提供的菜单、按钮、设置、空状态、加载提示、错误提示及自定义窗口文案。
- Mod 原始名称、作者描述、第三方日志以及操作系统原生对话框文案不承诺由应用翻译。
- 日期、数字等展示遵循当前语言的格式约定，避免在业务逻辑中手动拼接本地化文本。
- 改变语言时，当前界面和语言相关属性及时更新，不要求重启应用。

### 6.2 单文件新增语言（用户明确要求）

约定的语言目录中，每种语言用一个文件同时提供元信息和翻译内容。文件格式及目录位置在技术设计中确定，下例仅用于说明：

~~~json
{
  "meta": {
    "locale": "ja",
    "nativeName": "日本語",
    "direction": "ltr"
  },
  "messages": {
    "settings": {
      "title": "設定",
      "language": "言語"
    }
  }
}
~~~

新增语言应满足：

1. 仅新增一个符合规范的语言文件，无需修改语言导入列表、注册表、选择器选项、类型枚举、路由或打包配置。
2. 构建时自动发现、校验并包含语言文件；校验通过的语言自动出现在语言选择器中。
3. 选择器使用文件内的语言自称，用户无需先看懂当前界面语言才能识别自己的语言。
4. 发布后可以选择新语言，切换立即生效，重启后保留。
5. 语言内容作为数据处理，不在语言文件中执行任意程序逻辑。
6. 新增语言文件后需要重新构建和发布；第一版不要求运行时导入外部语言包。

### 6.3 校验与回退策略（提案）

- 建议以英语为基准语言和最终回退语言；这是统一策略，不是每添加一个语言都要修改的配置。
- 文件格式错误、语言标识重复、元信息无效、必需翻译键缺失或占位参数不一致，发布检查应失败，并明确指出文件和位置。
- 日期、复数、插值等内容使用统一约定；校验标准需覆盖约定中实际使用的格式。
- 首次启动优先匹配受支持的系统语言，无法匹配时回退到英语；用户明确选择后优先使用其设置。
- 保存的语言在新版中不存在时回退，避免应用无法启动。
- 即使有构建检查，运行时仍提供缺失键回退，避免出现空白界面或直接泄漏内部翻译键。
- 文本方向从语言元信息读取；基础布局应能按方向调整。以后增加 RTL 语言时不应为了基本方向切换而修改业务组件。
- 初始三种语言应检查字体显示、文本换行和长文案布局，不将固定宽度当作翻译长度限制。

### 6.4 国际化验收

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| I18N-01 | 依次切换三种初始语言并重启 | 应用文案更新，选择正确保存和恢复 |
| I18N-02 | 在临时验证分支中只新增一份完整的第四语言文件 | 构建通过，选择器自动出现新语言；发布产物可切换并恢复该选择；其他代码无变更 |
| I18N-03 | 添加重复标识、损坏文件、缺失必需键或参数错误 | 发布检查失败并给出可定位的错误 |
| I18N-04 | 设置包含已移除或未知语言 | 应用正常启动，使用约定回退语言 |
| I18N-05 | 注入较长文案和 RTL 测试语言 | 基础布局可读、控件可操作、方向符合元信息 |
| I18N-06 | 应用发生设置读写错误 | 使用当前语言显示应用提示，原始诊断信息可单独记录 |

第四语言和 RTL 语言仅用于验证扩展机制，不默认作为正式支持语言随产品发布。

## 8. 稳定性与验证原则

1. 正常流程与关键失败流程一起验收，包括配置损坏、目录无权限、未知语言和构建期语言文件错误。
2. 保存配置时避免留下部分写入的文件；恢复策略必须有行为验证。
3. 用户目录不能硬编码成某一个操作系统的路径；路径包含空格、中文或日文时应正常工作。
4. 耗时操作不能长时间阻塞主界面；没有准确进度时显示操作状态。
5. 应用基础功能无需联网；网络不可用不能阻止启动和切换语言。
6. 不把翻译键、内部命令名等实现细节当作正常产品提示。
7. 自动化优先覆盖设置恢复、迁移、国际化发现校验、通信失败等重要行为，配合各平台桌面运行验证。
8. 明确测试设备和环境后再制定启动耗时等数值目标；当前不承诺未经测量的性能数字。
9. “可扩展”通过一次新语言接入和一次示例模块接入验证；不以目录数量或抽象层数量作为完成依据。

## 10. 已解决与待解决的问题

### 10.1 本轮已解决

- 支持方向：Windows、macOS、Linux，并为未来其他平台扩展准备架构。
- 第一版定位：架构基础版，极少业务功能，以稳定健壮和易扩展为核心。
- 初始语言：简体中文、英语、日语。
- 新增语言方式：仅新增一个符合规范的语言文件，重新构建发布后可用。

### 10.2 基础版技术设计需要细化

1. 各桌面系统的最低版本、Linux 基准发行版及处理器架构支持矩阵。
2. 第一版是否公开发布安装包，以及各平台的分发方式。
3. 语言文件格式、自动发现机制、完整性校验和默认回退策略。
4. 统一错误结构、设置版本与恢复策略、跨平台适配边界。
5. 构建和桌面验证所用的环境与设备。

### 10.3 后续业务阶段再讨论

- SMAPI 随包内置的具体方式、版本及离线安装条件。
- 是否支持多个游戏目录或 Mod 配置方案。
- Mod 来源、在线下载更新、卸载和修复。
- 游戏与 SMAPI 版本兼容范围及分发许可要求。

不要求在架构基础版开始前决定所有后续业务细节。
